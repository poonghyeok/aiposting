도커를 활용해 애플리케이션을 배포할 때, 데이터베이스 비밀번호나 API 키 같은 민감한 정보를 어떻게 관리해야 할까요? 많은 초보 개발자가 `.env` 파일을 이미지 빌드 과정에 포함하는 실수를 범하곤 합니다. 하지만 보안과 유지보수 관점에서 이는 지양해야 할 안티패턴에 가깝습니다. 이번 글에서는 왜 환경 파일을 이미지에 포함하지 않고 실행 시점에 주입해야 하는지, 그리고 이를 `docker compose`로 구현하는 방법을 알아봅니다.

### 이미지 빌드에 `.env` 파일을 넣지 말아야 하는 이유

Docker 이미지는 한 번 빌드되면 레지스트리(Docker Hub 등)에 업로드되거나 여러 서버로 공유됩니다. 만약 빌드 시점에 `COPY` 명령어나 `ARG`를 통해 `.env` 파일을 이미지 레이어에 박아넣는다면, 이미지 내부의 파일 시스템에 비밀 정보가 고스란히 남게 됩니다. 

권한이 없는 사용자라도 이미지 레이어 히스토리를 역추적하면 민감한 정보를 쉽게 탈취할 수 있습니다. 따라서 빌드 결과물(Artifact)에는 환경에 종속된 비밀 정보를 배제하고, 순수한 애플리케이션 코드만 담는 것이 보안의 기본 원칙입니다.

### 런타임 주입의 핵심 원리

보안을 지키는 올바른 방법은 빌드와 실행(Runtime)을 분리하는 것입니다. 이미지는 환경에 구애받지 않도록 중립적으로 만들고, 실제 컨테이너가 실행되는 시점에 호스트의 환경 변수나 외부 파일(`--env-file` 또는 Docker Compose의 `env_file`)을 주입하는 방식입니다.

이렇게 하면 개발 환경, 스테이징 환경, 운영 환경에서 동일한 이미지 기본 파일을 사용하면서도, 각 환경에 맞는 서로 다른 설정값만 동적으로 다르게 적용할 수 있어 효율적입니다.

### Docker Compose 구현 예시

Docker Compose를 사용하면 `env_file` 옵션을 통해 간단하게 런타임 환경 변수를 주입할 수 있습니다. 아래는 전형적인 `docker-compose.yml` 파일의 예시입니다.

```yaml
version: '3.8'

services:
  app:
    image: my-web-app:latest
    ports:
      - "8080:8080"
    env_file:
      - .env
    restart: always
```

위 설정에서 `env_file`에 지정된 `.env` 파일은 이미지 내부로 복사되지 않습니다. 대신, 컨테이너가 생성되고 실행되는 순간 Docker 데몬이 해당 파일의 변수들을 읽어 컨테이너 내부 프로세스에 전달합니다. 따라서 `.env` 파일만 `.gitignore`에 등록하여 버전 관리 시스템(Git)에 노출되지 않도록 철저히 관리한다면 안전한 배포 파이프라인을 구축할 수 있습니다.

### 안전한 도커 라이프사이클을 향해

지금까지 Docker Compose 환경에서 `.env` 파일을 이미지에 포함하지 않고 런타임에 주입해야 하는 이유와 구체적인 설정 방법을 살펴보았습니다. 빌드와 설정을 분리하는 작은 습관이 프로젝트의 보안 수준을 한층 높여줍니다. 앞으로는 이미지 빌드 과정에 비밀 정보가 포함되지 않는지 다시 한번 점검해 보시길 바랍니다.
